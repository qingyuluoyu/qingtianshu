# 清数智算 Agent Demo

这是一个后端优先的金融研究 Agent MVP：行情事实与指标由确定性代码产生，Hermes 负责解释、追问和使用经用户确认的记忆。

当前实现：

- 19 个主要海内外指数的可审计目录，支持历史日线和指标；
- 中日韩美与伦敦金盘中行情、数据延迟和当日分钟 K 线；中日韩使用当前分钟指数源，美股收盘后保留最近收盘快照，并用交易所日历识别节假日、午间休市与提前收盘；
- A 股热门板块接口，包含来源、市场时间、抓取时间和降级状态；
- A 股全市场广度接口 `GET /markets/breadth`：逐页汇总沪深京 A 股上涨、下跌、平盘家数，覆盖不完整或涨跌字段缺失时拒绝确认固定分类；
- 东方财富公司公告、新浪个股新闻和按股票代码过滤的东方财富股吧情绪；
- A 股财报全文分页抓取与长期保存：按报告期提取毛利、财务费用、汇兑、存货、回款、经营现金流、减值和非经常性损益的原文说明，并把“公司明确解释”与“独立验证因果”分层；
- 腾讯实时估值快照，以及东方财富 F10 的结构化报告期财务指标；
- 确定性财报质量分析：比较上一年度同类报告期的营收/利润增速、毛利率、净利率、经营现金流覆盖和资产负债率，保存支持证据、矛盾、复核点与静态毛利率敏感性；
- 利润与现金流驱动拆解：A 股读取完整利润表、资产负债表和现金流量表，美股读取 SEC XBRL 详细科目；同类报告期量化毛利桥、费用率、营运资金、销售收现和三类现金流，并把机械影响、可疑线索与未确认业务原因分别保存；
- A 股主营业务结构分析：保存产品、地区、行业收入和毛利构成，严格区分最新收入报告期与可用毛利参考期，并支持同口径年报/中报比较、集中度复核和研究报告接入；
- 英伟达接入 SEC Companyfacts 财务、10-Q/10-K/8-K 官方监管文件、腾讯美股估值与 Nasdaq 公司相关新闻；
- 中兴通讯、中际旭创和英伟达均有固定可审计同行估值样本；A 股同行进一步比较同报告期营收、利润、毛利率、现金流转换和主营构成，报告期不匹配不进入中位数，也不生成公司排名或高低估评级；
- 后台自动刷新行情、A 股信息、A 股财报全文、主营业务结构、A 股与美股财务估值、财报质量、利润现金流驱动、历史校准、研究报告、研究结果回填和 Market Pulse，并通过事件流通知网页；
- 用户、安全会话、自选股、关注理由、记忆候选/确认和 Agent Run 统一存入 PostgreSQL；
- DeepSeek/ChatGPT 式多研究对话：新建、连续上下文、重命名 API、归档和跨用户隔离；桌面历史按日期分组，完全同题的旧会话默认折叠，活动旧会话自动保持可见，移动端下拉仍保留完整列表；
- 统一“研究 Agent”工作区：Hermes 按当前问题检索实时证据、资料库和金融 Skills；同一页保存多段历史对话，新对话首屏可直接继续最近研究，并按市场区域或证券代码自动呈现对应 K 线，个股同时显示 RSI14、MACD、ATR14 和 5/20 日量比；多股票策略问题会保存并恢复全部研究对象，先展示多股比较摘要，用户指定单只后再加载对应日 K 线；
- 问题驱动的个股 ResearchPlan：先把问题识别为行情原因、财务现金流、股东、主营、分析师预期、事件、估值同行或综合研究，再只加载相关证据模块和 Skills。当前用户自选股走 `watchlist_preanalysis`，刷新快变模块并允许慢变证据按时效复用；非自选股走 `online_research`，强制在线刷新行情、资讯、财务估值和事件，即使数据库中已有服务器报告也不会读取。只有自选股在线刷新失败时才允许按模块使用最近服务器证据回退；两条路径的本轮结论都由新的 Hermes/DeepSeek Run 即时生成，预生成报告正文永不冒充当前回答；
- 标准文字对话默认允许 4 次 Hermes 迭代，深入研究允许 6 次；标准个股继续使用 DeepSeek v4 Pro，但默认关闭额外 reasoning，以更快交付本轮事实。回答第一段必须先解决用户当前问题，再按实际证据动态组织依据、替代解释和核验边界；没有实质内容时不机械生成“候选事件”“反方证据”等固定栏目，必要金融术语会用一句话向普通投资者解释。未完整结束的 Hermes 文本和内部迭代错误不会作为正常答案显示；
- 金融顾问与教育者第二阶段：通用研究已覆盖基金、ETF、债券、利率、风险收益和资产配置基础知识，并新增基金/ETF产品事实库、产品名称或代码检索、同口径比较和后台持久化刷新。ETF明确归属于基金；口语中的“基金和ETF”按常见场外开放式基金与场内ETF解释，净值确认、连续成交报价、资金可用、到账、交收和完整成本分别保留具体产品与渠道边界。个人中心新增七项通俗风险问卷，答案先保存为草稿，只有用户明确确认后才进入 Agent 上下文。已确认画像会明确区分已知资金期限、回撤、应急储备、负债与仍缺的已有资产；纯概念问题不会因“小白”表达风格误入适合性路径，连续适合性追问不会丢失上下文；资料或确认不足时只解释选择逻辑并追问，信息齐全后只给条件化比较方向和核对项，不凭年龄、金额或“新手”标签指定唯一产品或承诺收益；
- 真实多股比较研究：自然语言可同时识别 2—5 只股票，跨轮恢复全部研究对象；只有报告日和累计/单季口径同时一致的财务指标才允许横向比较，跨币种不直接比较股价、市值和绝对金额，单只数据暂缺时仍保留其他标的的可用结果；
- 具名 A 股行业研究：类似“半导体行业怎么样”的问题会直接进入行业行情链路，读取官方行业指数历史、样本与权重、成分涨跌广度、同日全市场结构和市场资讯，再由 Hermes 针对本轮问题即时回答；不会把单一公司的财报或预生成报告当成行业结论；
- 一级入口使用直白任务名称：市场总览、透明选股、我的关注、个股研究、金融顾问、复盘中心、个人中心；金融资料库保留为资源入口，不再挤占一级导航；
- 市场总览按“全球行情 → A股一眼看懂 → 四个核心指数 → 市场Agent → 市场复盘文章 → 个人待办”组织。A股首屏直接展示涨跌家数、全市场涨跌中位数、当日累计成交额和领涨方向；市场文章只保留大盘内容，个股报告、机会和重复关注脉冲不再混入。Agent入口直接询问“今天市场发生了什么？”，并与页面使用同一份行情和市场证据；
- 统一搜索与 AI 提问分离：`GET /v1/search` 和 `/search?q=...` 按股票、行业、当前用户股票空间、历史对话与交易复盘分组展示结果；普通 Enter 打开完整搜索页，只有方向键显式选中联想项后才直接打开对象。行业结果进入透明选股并自动填写行业条件；“向 AI 提问”只预填问题，不自动创建对话或 Run；
- “今日观察”新增统一聚合接口 `GET /v1/today/overview`：首屏按高风险、到期任务、判断草稿确认和证据缺口展示最多 5 项，并同时返回上证综指、深证成指、创业板指、科创50、市场广度、成交、行业结构、与我相关的研究变化和盘前/盘中/盘后/非交易日状态；单个行情组件失败时，个人任务仍可独立返回。A 股指数在同一市场日期优先使用完整日线，不允许较晚的单点行情覆盖可计算收益和技术结构的历史；未完成来源与规则验收的自动事件不会伪装上线；
- 重要变化白名单闭环：公共 `change_events` 与用户 `user_change_links` 分表保存，当前只自动接纳官方财务披露，以及最近完整日线绝对涨跌达到 5% 的价格异常；盘中报价不会混入完整日线事件。`GET /v1/changes`、详情、已读和相关性 API 支持待判断、与我有关、与我无关状态，用户反馈不会修改公共事实。今日观察、顶部提醒和个股研究空间复用同一事件对象，详情抽屉统一展示事实时间、来源、数据状态、时间口径和研究边界；停复牌、限售解禁、股东增减持仍未通过逐类验收，不会提前展示；
- “个人中心”诚实基础版：读取当前用户真实关注股票、股票研究空间、历史对话、资料库文档和待处理研究项数量；首屏优先展示研究资产与由用户确认的风险画像，会话标识、服务状态、后台刷新、隐私和版本边界收进默认关闭的“服务、隐私与版本说明”。尚未实现的正式账号、会员计费、导出、账户删除、多设备和 BYOK 不做占位冒充；
- 个股 Agent 结构化回答与统一确认写回：普通个股研究以及财报质量、利润现金流、主营、股东、分析师预期和事件等专项研究，都会在自然语言正文之外保存事实、证据推断、反方证据、待验证假设、信息缺口、需要重新判断的情况、下一步核验和逐 Claim 引用；用户明确要求时可生成判断、观察任务、操作计划或交易复盘草稿候选，确认前不修改正式对象，确认、拒绝、重复确认、版本冲突和跨用户隔离均由同一后端协议处理；
- Agent 观察任务确认闭环：用户明确说“保存为核验任务”或“创建观察任务”时，系统从本轮结构化 `next_evidence_tasks` 整理待确认候选；模型只返回研究文本，不能自行写文件、数据库或任务。用户点击确认后才调用正式任务服务，列表、刷新恢复、用户隔离和重复确认幂等均由后端保证；
- “透明选股”同时提供独立一级页面和自然语言入口，可选择经营改善、相对行业增强、估值约束和回撤待复核四类透明模板，也可解析“筛选A股”“经营改善模板/候选”“相对行业增强”“估值约束”“回撤后待复核”，以及 PE、PB、市值、ROE、营收/净利润增速、行业和市场范围；确定性引擎执行筛选，统一返回内容哈希数据版本、股票池/市值/估值/20日收益/财务候选池覆盖率、行情日、5/20日基准日、财务报告期、公告日、逐字段缺失原因和来源合同。Hermes/DeepSeek 只解释本轮确定性结果，候选总数必须与引擎一致，带证券代码的上市公司“东方财富”不会再被误当成数据源名称删除；不计算综合分或买卖信号。候选可保存为研究线索，或直接进入该股票唯一的长期 Agent 对话继续核验；
- “李总策略”独立执行全A股确定性筛选：先发布并按同一请求日复用最近完整交易日的全市场名单和市值快照，再对市值严格大于150亿元的股票预判上市后量价窗口；只有量价历史客观不足时才直接保存为数据不完整，不消耗逐股深度请求。预判按 A 股约 242 个交易日/年的市场日历并增加节假日缓冲，避免把只有 377 条行情的近期上市股票误送入 380 日深度规则。上市未满五年不会被当成 ROE 必然缺失，因为公开财务数据可能包含上市前年度，必须实际查询后判定。其余股票按历史完整性、既有数据可得性和市值分批补齐 ROE、股东、复权日线和真实涨跌停价。年度 ROE 以 Tushare 为主；若某一必需年度的直接值缺失，仅使用已有的东方财富 F10 结构化 Provider 补该年度，不覆盖 Tushare 已有值，并把公告日、来源 URL 和补充原因写入规则证据。网页和 Agent 分开说明全市场名单、可深度核验、深度处理进度、量价历史不足和候选数量，不再把名单状态覆盖率冒充深度规则完成率；支持在同一问题中解析多个全市场公司名称并逐股回答，用户页面会清理内部状态枚举和供应商错误。后台批次通过事件流自动刷新透明选股页。日线、复权和涨跌停价在同一次逐股同步中统一预留 1150 个市场交易日，为3年回测额外保留380日规则预热区间，并减少长期停牌造成的假性历史不足；旧短窗口缺口只按数据窗口版本重算一次。当前候选为空时，页面继续展示逐规则筛选漏斗，并从近期无前视历史回放中列出曾经真实进入候选或触发阶段的股票；每个事件保存当时逐规则证据、信号后 5/10/20 个交易日个股与沪深300表现、超额收益和路径最大上行/下行。`GET /v1/stock-strategies/li-zong/history` 读取历史事件，管理员可用 `POST /v1/stock-strategies/li-zong/history/runs` 指定股票或小批量补算。历史回放默认只覆盖最近 80 个可计算交易日，不能表述为多年全市场回测；
- 李总策略新增独立的组合级长期验证：后台按历史交易日一次获取全 A 股 `daily_basic` 截面，只保存当日总市值严格大于150亿元的股票；再以1150个交易日量价、8年ROE和5年股东披露逐日运行同一版本规则。候选信号最早在下一交易日开盘执行，任意两次实际换仓至少间隔10个交易日；冷却期内候选继续更新，但只执行最新集合。候选为空时持有现金，本版不计交易成本；沪深300按完整回测区间每日收盘连续计算，策略空仓期指数仍继续变化并计入相对收益比较。系统按63、252、756个交易日分阶段建设和发布，未完整的长窗口不会把缺失市值按0提前计算；稳定快照优先选择最新数据日期，供应商迟到重试不会让事实时间倒退。历史市值提示只提供该日市值，不得截断日线、复权因子和涨跌停价查询；正常上市股票的尾部行情缺口保存为 `data_incomplete`，区间内停牌才允许延续价格，明确退市后使用最后可得复权收盘价作为强制退出代理。上市前自然没有行情的交易日不算数据缺口；一旦出现首个真实复权收盘价，后续任何规则或行情无法形成确定状态的日期都会把该股票如实计入缺口覆盖。后台先补阻塞3个月发布的股票，再补1年，最后扩展3年；单批最多补齐12只逐股数据，同时请求仍限制为4只。`requested_as_of_date` 作为数据库元数据保存，后台无需加载整份历史 JSON 就能识别已查询到窗口末端的股票。上游明确返回缺失ROE、股东或复权数据时，该股票逐日保存为 `data_incomplete`，不会被当作候选，并在最终结果中披露完整数据数量、缺口数量和覆盖率，不让少数永久缺口无限阻塞整个回测。历史逐日规则使用与原始逐日调用逐项等价的滚动计算引擎，并保留版本化输入指纹，价格、财务、股东或历史市值版本变化时自动失效重算。普通用户通过 `GET /v1/stock-strategies/li-zong/backtest?period=3m|1y|3y` 查看建设百分比、数据缺口、区间收益、年化收益、最大回撤、换手、净值曲线和换仓记录。管理员可用 `POST /v1/stock-strategies/li-zong/backtest/runs` 推进批次。完整流水线见 `docs/PRODUCT_PIPELINE_ARCHITECTURE.md`；

### 方式一：使用 uv（推荐）

# 修改 .env 中的 QINGSHU_DATABASE_URL，并确保目标 PostgreSQL 数据库已创建

### 结构化回答与判断确认 API

个股普通研究和财务、主营、股东、预期、事件等专项对话响应及历史消息 `metadata` 会包含
`structured_answer`。其主要字段为：

- `answer_summary`
- `confirmed_facts`
- `evidence_based_inferences`
- `hypotheses_to_verify`
- `counter_evidence_and_risks`
- `information_gaps`
- `invalidation_conditions`
- `next_evidence_tasks`
- `conclusion_boundary`
- `citations`
- `candidate_writebacks`

引用和候选写回会持久化到 PostgreSQL；公开响应不会返回 `user_id`、
`workspace_id`、`conversation_id`、内部 `source_key` 等字段。当前 R1
已经开放四类确认写回：版本化当前判断 `thesis`、用户观察任务
`observation_task`、操作计划 `action_plan` 和交易复盘草稿 `review_draft`：

- `GET /v1/ai-writebacks`
- `GET /v1/ai-writebacks/{candidate_id}`
- `POST /v1/ai-writebacks/{candidate_id}/confirm`
- `POST /v1/ai-writebacks/{candidate_id}/reject`

普通问题不会产生判断草稿。可以明确询问：

> 分析中兴通讯当前的支持证据和反方证据，说明什么情况会推翻当前判断，并形成判断草稿供我确认；不要直接修改正式判断。

Agent 失败、守卫未完成或只返回 preview 时不会创建候选。确认时若正式判断或复盘版本
已经变化，接口返回 `409` 并把旧候选标记为 `stale`。用户明确要求“创建观察任务”或
“保存为核验任务”时，Agent 会把本轮 `next_evidence_tasks` 整理为候选；明确要求生成操作计划时，
只保存用户本人给出的核验条件，不把行情价、均线、估值或模型推导的比率改造成触发门槛。
复盘生成接口也先返回 `review_draft` 候选。确认前不会创建正式任务、计划或复盘版本，确认后才进入
相应领域列表，重复确认不会重复创建。

四类确认写回、确定性后端完整链、桌面真实浏览器交易复盘链、仓库内只读浏览器 Runner 和 390px 核心页面验收已经完成，但这不等于生产 R1 已完成；类型、契约、正式前端构建、认证、生产数据底座和发布恢复等门禁仍待封口。

## 服务器后台运行

- 每 10 分钟刷新默认 A 股及全部用户自选股的公告、新闻和社区情绪；
- 每小时发现并保存默认 A 股及全部用户自选股最近三份财报全文，内容不变时跳过重复下载，并刷新原文原因摘录和长期通用资料；
- 每小时刷新默认 A 股及全部用户自选股的产品、地区、行业主营构成和同口径比较，并写入长期通用资料；
- 每小时刷新默认 A 股及全部用户自选股的股东户数、十大股东和股权结构快照，并写入长期通用资料；
- 每小时刷新默认 A 股及全部用户自选股的券商评级分布、A/E 每股收益预测、近期研报元数据与历史修订边界；
- 每小时刷新 A 股实时估值与结构化财务报告期；
- 每小时刷新英伟达的腾讯美股估值、SEC 财务与 10-Q/10-K/8-K；
- 每小时为默认研究标的和用户自选股刷新同类报告期财报质量分析，并写入长期通用资料库；
- 每小时基于已落库详细三表刷新利润、费用率、营运资金和现金流驱动分析，并写入长期通用资料库；
- 每小时刷新三只默认标的及其九只固定同行的估值快照，并为 A 股固定同行刷新同报告期经营和主营构成快照；
- 每 6 小时用五年复权日线刷新 5/10/20 日走查校准；
- 每 30 分钟为中兴通讯、中际旭创和英伟达刷新服务器研究报告；
- 每 30 分钟扫描历史研究时点，并按 T+3/T+5/T+10 回填研究条件和价格路径；
- 每 10 分钟预先刷新美股、A 股、港股、日股、韩股、欧股和伦敦金的市场驱动资讯并入库；
- 每 30 分钟检查一次 Market Pulse 发布条件，符合质量、变化和频率门槛后自动发布，并通过 `/events` 事件流通知网页。
- 每分钟执行数据质量审计并写入 PostgreSQL；详细检查只通过 `/system/data-health` 提供给运维，网页只显示“数据已连接”或“部分数据同步中”。
- 李总策略使用独立后台线程：先建立全市场稳定市值快照，再按 `LI_ZONG_UNIVERSE_BATCH_SIZE` 分批补齐高市值股票的多年规则数据；每批完成后等待 `LI_ZONG_REFRESH_SECONDS` 再继续，不阻塞实时行情和其他后台任务。深度规则仍有待处理股票时，每轮同时推进最多 2 只近期历史回放；深度规则空闲时每轮推进最多 5 只，使“当前候选为空”也能逐步形成可复盘的真实历史样本。

Docker 方式：

```bash
export POSTGRES_PASSWORD='<use-a-long-random-password>'
export QINGSHU_ADMIN_API_TOKEN='<use-another-long-random-value>'
docker compose up --build -d
```

Compose 会启动四个服务：

- `postgres`：保存用户、会话、自选股、研究对话、证据、分析结果、周期计划、任务租约和重试状态；
- `qingshu-agent`：只提供 Web/API，不在 Web 进程中执行后台刷新；
- `qingshu-worker`：从 PostgreSQL 原子抢占任务并执行，可用
  `docker compose up --scale qingshu-worker=2` 扩展 Worker。
- `qingshu-backup`：启动后立即创建一次 PostgreSQL 自定义格式备份，之后默认每天
  备份；备份保留 14 天且至少保留最近 7 份，并用独立持久卷保存。

Web 和多个 Worker 首次同时启动时，业务库与运维库分别使用 PostgreSQL 事务级
advisory lock 串行执行 Schema 初始化，避免并发 `CREATE/ALTER` 竞态。

### Staging 验证

仓库提供不含真实凭据的 `staging.env.example`。复制后替换密码和管理员 Token；
`COMPOSE_PROJECT_NAME=qingshu-staging` 会让数据库、工作区和备份卷与生产完全隔离：

```bash
cp staging.env.example .env.staging
docker compose --env-file .env.staging up --build -d

curl http://127.0.0.1:18000/health
docker compose --env-file .env.staging exec qingshu-worker \
  python scripts/check_operations.py \
  --require-postgres \
  --minimum-active-workers 1 \
  --skip-backup

docker compose --env-file .env.staging exec qingshu-backup \
  python scripts/postgres_backup.py \
  --output-dir /backups \
  --check-max-age-seconds 93600
```

停止 staging 使用 `docker compose --env-file .env.staging down`；不要加 `-v`，
除非明确要销毁 staging 数据和备份。

用户工作区文件仍保存在 `qingshu-data` volume；生产多机部署应再迁移到共享文件系统或对象存储。容器默认使用无需模型费用的确定性 preview；生产 Hermes Provider 应通过云端密钥管理接入。

本地和生产运行都必须设置 `QINGSHU_DATABASE_URL`；未配置或不是 PostgreSQL 地址时应用会拒绝启动，不会静默创建 SQLite。开发环境可以使用
`BACKGROUND_WORKER_MODE=embedded` 在 Web 进程内运行同一套 PostgreSQL 持久化队列；生产建议使用独立 Worker：

```bash
export QINGSHU_DATABASE_URL='postgresql://qingshu:***@db-host:5432/qingshu'
export BACKGROUND_WORKER_MODE=external

# Web
uv run uvicorn app.main:app --host 0.0.0.0 --port 8000

# 独立 Worker
uv run qingshu-worker
```

生产 Worker 会写入持久化注册表。运维端可看到进程、队列、最近心跳、当前任务、
累计领取/成功/失败数；心跳过期会标记为离线。队列指标同时提供 ready/delayed、
重试中任务、最老待执行任务延迟、过期租约、最近 24 小时成功/失败与失败率，以及
租约恢复累计次数。

数据健康任务会清理终态队列历史，避免分钟级任务无限增长：成功和取消任务默认保留
7 天，失败归档默认保留 30 天，等待和运行任务永不被保留策略删除。可通过
`JOB_SUCCEEDED_RETENTION_HOURS`、`JOB_FAILED_RETENTION_HOURS` 和
`JOB_CANCELLED_RETENTION_HOURS` 调整。业务库中的后台成功审计和数据健康快照默认
保留 30 天，失败审计保留 90 天；运行中的审计永不清理。

### PostgreSQL 备份与恢复

Compose 默认参数可通过以下环境变量调整：

```bash
export QINGSHU_BACKUP_INTERVAL_SECONDS=86400
export QINGSHU_BACKUP_RETENTION_DAYS=14
export QINGSHU_BACKUP_MINIMUM_RETAINED=7
export QINGSHU_BACKUP_MAX_AGE_SECONDS=93600
```

本机或独立备份主机也可直接运行：

```bash
uv run python scripts/postgres_backup.py \
  --database-url "$QINGSHU_DATABASE_URL" \
  --output-dir ./backups

uv run python scripts/postgres_backup.py \
  --output-dir ./backups \
  --check-max-age-seconds 93600
```

备份只有在 `pg_dump` 成功、文件非空且 `pg_restore --list` 能解析归档后才会原子
发布并更新 `latest.json`；manifest 同时保存 SHA-256，损坏的临时归档不会成为
“最近成功备份”。

恢复是破坏性操作，必须逐字确认目标数据库名。日常演练优先使用临时数据库恢复
脚本，它会校验备份 SHA-256、恢复核心业务表和队列表、检查两个 Schema 版本与
关键行数，然后自动删除临时库：

```bash
uv run python scripts/postgres_restore_drill.py \
  ./backups/qingshu-YYYYMMDDTHHMMSSZ-xxxxxxxx.dump \
  --database-url "$QINGSHU_DATABASE_URL"

uv run python scripts/postgres_restore.py \
  ./backups/qingshu-YYYYMMDDTHHMMSSZ-xxxxxxxx.dump \
  --database-url "$QINGSHU_DATABASE_URL" \
  --confirm-database qingshu \
  --clean
```

执行恢复演练的数据库用户需要 `CREATEDB` 权限。数据库备份不包含用户工作区文件；
多机生产部署仍应把工作区迁往对象存储，或为共享文件卷建立独立快照与恢复策略。

已有 SQLite 数据迁移前，应先备份数据库和用户工作区。迁移工具只读源 SQLite，
要求目标业务表为空，逐表复制后核对行数：

```bash
uv run python scripts/migrate_sqlite_to_postgres.py \
  --source ./data/qingshu.db \
  --source-workspace-root ./data/workspaces \
  --workspace-root /data/workspaces \
  --database-url "$QINGSHU_DATABASE_URL" \
  --dry-run

uv run python scripts/migrate_sqlite_to_postgres.py \
  --source ./data/qingshu.db \
  --source-workspace-root ./data/workspaces \
  --workspace-root /data/workspaces \
  --database-url "$QINGSHU_DATABASE_URL"
```

提供 `--source-workspace-root` 后，`users`、`user_uploads` 和 `runs` 中的
`workspace_path` 会按相对目录安全重写到目标根目录；任何路径落在源根目录之外都会
终止迁移。工具只改数据库引用，不复制文件，切换前还必须把源工作区目录完整同步到
目标共享卷，并在目标容器内核对抽样文件。源库存在工作区路径时，未提供
`--source-workspace-root` 会直接停止；只有确认源路径在目标环境仍有效时，才能显式
使用 `--preserve-workspace-paths`。

## 开启 Hermes

复制 `.env.example` 中需要的变量到你的进程环境。最小方式：

```bash
export HERMES_ENABLED=true
```

然后在 `/chat` 请求里传：

```json
{
  "message": "分析我的自选股",
  "model_tier": "economy",
  "execute_agent": true
}
```

模型路由读取：

- `HERMES_ECONOMY_PROVIDER` / `HERMES_ECONOMY_MODEL`
- `HERMES_DEEP_PROVIDER` / `HERMES_DEEP_MODEL`
- `HERMES_VISION_PROVIDER` / `HERMES_VISION_MODEL`

文字对话未设置路由时默认使用 `custom / step-3.7-flash`，通过 `CUSTOM_BASE_URL=https://api.stepfun.com/v1` 连接阶跃星辰的 OpenAI 兼容接口；显式环境变量仍可覆盖。视觉路由未设置时由 Hermes 的多模态配置决定。阶跃密钥使用 `STEPFUN_API_KEY`，只由 Hermes 或进程环境读取，不写入仓库。

一键启动检测到 `HERMES_BIN` 后会启用 Hermes，文字对话默认路由到 StepFun；如需其他模型，可用上述环境变量覆盖。密钥只由 Hermes 或进程环境读取，不写入项目。

`HERMES_BIN=hermes` 会按当前进程的 `PATH` 解析，不要求写本机绝对路径。流式回答会从 Hermes 控制台脚本或启动包装器识别其虚拟环境 Python，并保留虚拟环境入口；只有非标准安装无法自动识别时，才需要设置 `HERMES_PYTHON_BIN`。应用不会读取或复制 Hermes 密钥。

Hermes 返回后会经过 `deterministic_numeric_and_policy_guard_v2`：守卫理解“涨 / 跌 / 回撤”的语义方向、合理四舍五入和由确定性证据计算出的均线距离等派生值。大盘回答只使用模型实际收到的当前市场、当前问题证据校验，不会让其他市场数字或上一轮助手措辞成为可信事实；用户输入中的数字也不会因此放行。守卫仍拒绝证据外数字、反向改写、目标价、未来涨跌概率、收益保证、浪型判断以及 BUY/HOLD/SELL 指令，并拦截原始字段名、后台状态、供应商名称和数据源故障。若回答只包含少量不受支持的句子，系统会删除对应句子后再次完整验守，尽量保留其余针对性模型回答；交易复盘的结构化 JSON 会按字段删除越界子句，不再因为整段位于同一行而丢弃完整即时回答。涉及策略禁令、语义冲突或无法安全修复时，才退回确定性摘要。原始被拒文本只留在该用户 Run 目录用于诊断。

“诊大盘”会直接执行 Hermes，而不是先把固定市场模板当成最终回答。后端按当前问题区分趋势反转、量能资金、板块轮动、涨跌原因和市场风险五类焦点，只保留该问题需要的指标、板块、实时资讯、已确认用户记忆和 `market-brief` Skill。大盘 Prompt 固定带入“证据层级、市场因果、趋势风险”三份通用资料；连续追问只保留最近用户问题并继承市场范围，不把上一轮模型回答重新当作写作模板。若模型超时，确定性摘要也会按本次问题焦点回答，不再退回同一份全景模板。

多模态请求使用 Hermes 的 `chat -q --image` 路径。网页先通过 `POST /me/uploads/images` 上传图片，对话只传服务器生成的 `image_id`；客户端不能传本机路径。后端会验证图片归属，Hermes 只能读取当前用户专属工作区内的已消毒副本。图像回答通过显式最终答案协议去除 CLI 推理文本，然后再进入金融数字和策略守卫。

文档研究通过 `POST /me/knowledge` 上传 PDF、DOCX 或 XLSX。服务端使用 MarkItDown 的内存流接口转换为 Markdown，不启用插件、不读取远程 URL；原文件保存在当前用户工作区，转换文本进入个人资料库检索链路。默认单文件上限为 20 MiB。当前版本不对扫描版 PDF 启用 OCR，未提取到可读文字时会明确拒绝入库。

## 持久化后台任务

市场刷新、资讯、财报、研究报告、证据任务、数据健康、李总策略和文章发布评估都使用数据库持久化队列。任务包含幂等键、到期时间、优先级、尝试次数、租约所有者、心跳、结果和错误；PostgreSQL Worker 通过 `FOR UPDATE SKIP LOCKED` 防止多实例重复抢占。Worker 异常退出后，租约到期的任务会重新入队；失败按指数退避重试，达到最大尝试次数后进入失败归档，可由管理员重试。

任务执行语义是 at-least-once，后台处理函数必须保持幂等；同一周期任务在已有
`queued/running` 实例时会合并，不会无限堆积。

Worker 产生的市场更新、文章发布和数据健康事件会先写入数据库事件表，再由 Web
进程统一轮询并推送 `/events` SSE；因此 Web/Worker 分进程后仍能实时更新页面，
不会依赖某个进程内存中的临时订阅者。事件默认保留 48 小时并由数据健康任务清理。

PostgreSQL 连接池默认每进程业务库最多 8 条、运维库最多 4 条，避免 Web 加多个
Worker 时迅速耗尽服务器连接。可通过 `QINGSHU_DB_POOL_*` 和
`QINGSHU_OPERATIONAL_DB_POOL_*` 调整；管理员运维报告会返回两类池的当前统计。

`scripts/publish_market_pulse.py` 只是开发人员单独验证文章逻辑时使用；系统只有在证据质量达标、距离上一篇至少四小时、市场结构指纹变化且未超过 24 小时三篇上限时才真正生成文章。

```bash
uv run python scripts/publish_market_pulse.py
```

需要后台模型润色时同时设置 `HERMES_ENABLED=true` 和
`BACKGROUND_USE_HERMES=true`。本地默认嵌入式 Worker，生产 Compose 默认独立
Worker；两种模式使用相同的数据库任务合同。

后台管理接口不会显示在用户网页，且同时要求个人会话和
`X-Qingshu-Admin-Token`：

- `GET /admin/job-queue`：查看队列健康和任务；
- `GET /admin/job-schedules`：查看周期计划、配置启用状态和人工暂停状态；
- `POST /admin/job-schedules/{name}/pause`：停止该计划后续入队，不中断已运行任务；
- `POST /admin/job-schedules/{name}/resume`：清除人工暂停；仅在配置允许时恢复执行；
- `GET /admin/operations/health`：查看数据库 Schema、队列延迟与失败率、Worker
  心跳和最近备份状态；
- `POST /admin/job-queue/enqueue`：手工幂等入队已注册任务；
- `POST /admin/job-queue/{job_id}/retry`：重试失败/取消任务；
- `POST /admin/job-queue/{job_id}/cancel`：取消尚未执行的任务。

部署探针无需登录网页，可在服务器内直接检查同一组生产条件并以退出码表示结果：

```bash
uv run python scripts/check_operations.py \
  --require-postgres \
  --minimum-active-workers 1 \
  --max-queue-lag-seconds 600 \
  --max-failure-rate-24h 0.2
```

Worker 容器健康检查使用该脚本的无备份模式；备份容器单独检查最新备份年龄。
Web 的 `/health` 只表示进程存活，`/ready` 才检查 Schema、队列和所需 Worker；
Compose Web 健康检查使用 `/ready`，后台不可运行时会返回 HTTP 503。

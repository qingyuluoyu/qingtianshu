# 个股评分库性能与五维布局设计

日期：2026-07-25  
状态：已确认，待实施

## 1. 目标与边界

本轮解决两个已复现问题：

1. 个股评分库会在 Web 请求中同步等待外部行情，缓存过期后单次请求约需 15 秒，无法支持数千用户并发。
2. 五维行业对比在宽屏中雷达图过小、指标卡信息密度低、存在大面积空白，估值柱状图的基线和标签位置不稳定。

本轮不增加新的评分模型，不改变既有公式版本，不引入券商接口，也不把静态结果冒充实时数据。

## 2. 当前证据与根因

2026-07-25 在本地运行服务上测得：

| 请求 | 第一次 | 第二次 | 结论 |
| --- | ---: | ---: | --- |
| `score-card` | 15.307 秒 | 15.220 秒 | 每次同步等待分钟行情上游 |
| `industry-comparison` | 2 毫秒 | 3 毫秒 | 持久化快照命中，五维计算并非每次执行 |
| 日 K 线 | 15.183 秒 | 3 毫秒 | 冷请求等待上游，进程内缓存命中后快速 |

直接原因如下：

- `StockDashboardService.score_card()` 在请求线程内调用分钟行情接口。
- Yahoo 请求超时为 15 秒，而分钟行情缓存默认仅 20 秒。
- 行情缓存过期后，数据库中的陈旧数据只有在上游失败后才回退，因此用户仍需等待完整超时。
- K 线的快速缓存主要位于单个 Web 进程内，多个实例之间不能合并冷请求。
- “刷新个股数据”对行业对比传递 `refresh=true`，会绕过现有快照并同步重建同行截面。
- 行业预热只有单进程单线程执行器，不适合随用户关注股票数量线性扩张。

## 3. 方案选择

采用“持久化快照 + 后台刷新任务 + 分布式去重”的 stale-while-revalidate 模式。

不采用以下方案：

- 只延长进程内缓存：无法解决多实例重复请求和重启冷启动。
- 继续同步请求并缩短超时：仍然让供应商延迟进入用户请求链路，且容易形成请求放大。
- 只增加浏览器缓存：不能形成服务器侧统一事实来源，也无法安全控制数据版本和刷新。

## 4. 数据读取与刷新架构

### 4.1 Web 读取路径

评分页的三个公共数据模块独立返回：

- 行情与主卡快照；
- K 线快照；
- 行业评分与同行统计快照。

Web 请求只读取 PostgreSQL/Redis 中最近一次成功快照，不直接等待 Yahoo、Tushare 或完整行业计算。

读取规则：

1. 新鲜快照：直接返回，状态为 `fresh`。
2. 已过期但仍在允许陈旧窗口内：立即返回，状态为 `stale`，并提交后台刷新。
3. 没有快照：快速返回 `warming`，提交后台刷新。
4. 最近刷新失败：返回最近成功快照及结构化失败状态，不删除可用快照。

页面首屏目标是缓存命中时 300 毫秒内完成服务器响应。该数值是本轮验证目标，不作为尚未压测的正式服务等级承诺。

### 4.2 后台刷新任务

沿用项目既有持久化研究队列、Redis 和 Worker 体系，不建立第二套队列。

刷新任务至少包含：

- `task_id`
- 数据类型
- 标准化 A 股证券标识
- 数据日期或报告期
- 方法版本
- 幂等键
- 当前状态
- 尝试次数
- 下次重试时间
- 错误分类
- request/trace 标识

幂等键建议：

- 行情：`stock-quote:{symbol}:{market-session}`
- K 线：`stock-kline:{symbol}:{period}:{adjust}:{market-session}`
- 行业评分：`industry-score:{sw2-code}:{report-period}:{valuation-date}:{formula-version}`

相同幂等键在 queued、leased 或 running 状态时只允许一个有效任务。用户点击刷新只返回当前快照和刷新状态，不创建无限重复任务。

### 4.3 数据更新周期

不同数据采用不同新鲜度：

- 交易时段行情：短周期，由集中行情刷新任务更新。
- 收盘 K 线：交易日收盘后更新；非交易日复用最近交易日快照。
- 财务数据：按公告或报告期变化刷新。
- 行业同行截面：按行业、报告期、估值日期和公式版本批量计算。

行业评分不按“用户 × 股票”重复计算。同一申万二级行业、同一报告期和估值日期的公共截面只构建一次，再生成各证券结果。

### 4.4 多实例与并发

- PostgreSQL 保存可恢复的快照与任务事实。
- Redis 用于短期缓存、刷新任务投递和分布式去重。
- Web 实例只读取快照和快速入队。
- Worker 执行外部调用与计算，并受全局并发、供应商并发和超时限制。
- 缓存键必须包含市场、证券、数据日期、调整方式和方法版本。
- 公共行情和公共评分可跨用户复用；用户私有研究和持仓不能进入公共缓存键。

## 5. 接口状态契约

评分模块响应增加兼容字段，不删除现有字段：

```json
{
  "cache": {
    "state": "fresh | stale | warming | refresh_failed",
    "refreshing": false,
    "generatedAt": "ISO-8601",
    "dataAsOf": "ISO-8601 or market date",
    "nextRefreshAfter": "ISO-8601 or null"
  },
  "refresh": {
    "taskId": "string or null",
    "status": "idle | queued | running | failed",
    "lastErrorType": "string or null"
  }
}
```

手动刷新接口或现有兼容参数不得同步执行完整刷新。它只进行权限、限流和幂等检查，返回 HTTP 202 或保持现有 HTTP 200 兼容响应，并附带任务状态。

前端不得因为 `stale` 隐藏现有数据；应同时展示数据截止时间和“更新中”状态。

## 6. 错误与降级

- 供应商超时、限流和临时不可用：有限重试，保留最近成功快照。
- 参数错误、不支持的证券、权限错误：不可重试。
- 没有任何历史快照：显示“首次准备中”，不显示零值或模拟结果。
- 刷新任务失败：展示“最近数据仍可查看，更新失败”，提供可追踪任务标识。
- 非交易日：数据截止时间必须指向最近交易日，页面更新时间单独展示。

## 7. 五维行业对比布局

### 7.1 桌面端

- 模块采用约 400px 的雷达图列和自适应内容列。
- 雷达图高度约 320px，轴标签使用 11–12px，数值标签使用 10–11px。
- 雷达图同时保留当前公司和行业中位两条系列。
- 指标卡改为两列流式布局，不再使用固定六列的 3+2 居中排列。
- 第五张卡与“如何理解分数”说明共同填充末行，避免大面积空白。

每个指标卡展示：

- 维度名称；
- 0–100 相对分数；
- 行业位置描述；
- 覆盖率；
- 一句话定义。

分数描述沿用现有确定性区间：

- 80–100：行业领先
- 65–80：相对较强
- 35–65：行业中游
- 20–35：相对较弱
- 0–20：行业靠后

维度说明只解释当前公式，不新增指标：

- 成长性：收入与利润增长相对同行的位置。
- 估值水平：PE、PB 等估值指标相对同行的位置，方向以现有公式为准。
- 盈利能力：ROE、ROIC 和利润表现相对同行的位置。
- 财务稳健性：偿债能力、负债结构和盈利波动相关指标。
- 经营效率：资产周转、现金回收和经营投入效率。

### 7.2 估值与指标柱状图

- 为每组指标独立计算正负值域。
- 零基线必须在绘图区内清晰可见。
- 正值标签放在柱顶上方，负值标签放在柱底下方，并钳制在画布边界内。
- 当前公司、行业中位和行业上四分位保持固定颜色及图例。
- 不同单位的指标仍按分组独立缩放，不能将 PE、ROE 和增长率放入同一绝对纵轴比较。

### 7.3 移动端

- 雷达图与指标卡改为单列。
- 雷达图宽度跟随容器，保持不少于 280px 的有效绘图区。
- 指标卡不横向滚动，分数、描述和覆盖率不得互相遮挡。

## 8. 前端交互

- 首次进入立即展示已有快照，不把整个页面置为全局不可用。
- 三个数据模块独立加载和更新，一个供应商失败不能清空其他模块。
- 点击刷新后按钮显示“更新中”，但页面仍可阅读。
- 后台任务完成后自动重新读取对应模块；轮询设置最大次数和退避间隔。
- 页面明确区分“数据截止时间”“页面更新时间”和“后台刷新状态”。

## 9. 测试与验证

### 9.1 自动化测试

- 新鲜快照不调用上游。
- 陈旧快照立即返回并只入队一次。
- 无快照返回 `warming`，HTTP 请求不等待供应商超时。
- 多个并发请求使用同一幂等键，只产生一个刷新任务。
- Worker 成功后原子替换快照。
- Worker 失败保留最近成功快照。
- 手动刷新不再同步重建行业截面。
- 非交易日使用最近交易日。
- 五维卡片包含名称、分数、描述、覆盖率和定义。
- 柱状图具备零基线和正负标签边界处理。

### 9.2 运行验证

- 运行受影响单元测试、接口测试和前端契约测试。
- 运行完整 API 与非 API 回归。
- 测量热缓存、陈旧缓存、无缓存和并发刷新耗时。
- 1440×900 检查雷达图、指标卡、柱状图和空白区域。
- 390×844 检查单列布局、图表文字、按钮和横向溢出。

## 10. 兼容、迁移与回滚

- 现有响应字段保留，新增缓存和刷新状态字段。
- 如现有快照表不足，使用 expand 迁移增加版本、状态和刷新元数据，不删除旧字段。
- 部署顺序为迁移、Worker、Web、前端。
- 回滚时旧 Web 可继续读取原有快照字段；新增后台任务可停止消费，不影响已有评分数据。
- 不在应用启动时同步回填全部股票。历史预热使用可恢复的批处理任务。

## 11. 成本与容量约束

- 同一公共数据快照跨用户复用，避免用户数量直接放大供应商调用量。
- Worker 对每个供应商设置并发上限、超时和有限重试。
- 热门股票优先刷新，长尾股票按访问触发但必须去重。
- 记录供应商调用次数、耗时、失败率、缓存命中率和任务积压。
- 本轮不虚构具体峰值容量；完成并发压测后再确定正式容量和服务目标。
